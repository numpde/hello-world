Hello World: how new projects should work
========================================

9 November 2026
Repository: numpde/hello-world
Plan for the template; written before implementation.

The aim
-------

A new project should be useful from the first checkout. Running make
should explain the available commands. After explicitly downloading its
dependencies, a developer should be able to build, test, and run the
project without surprise downloads or unwanted temporary files left behind.

Keep the common tools small. Packages, command-line tools, backends,
frontends, and mixed projects should share those tools. Add database,
browser, GPU, and publication support only when a project needs it.

What is enforced, and what needs judgment
----------------------------------------

At this revision hello-world contains this note, not the proposed tools.
None of the mechanisms below is implemented here yet.

Part A describes rules to build into the common tools. Part B describes
extra mechanisms for projects with particular features. Each section
names the implementation and checks that could enforce its concrete rules.
These become claims of enforcement only when the mechanism exists and
the relevant checks run in the supported environment.

Part C contains engineering guidelines and review expectations. They
include aims such as clear architecture, helpful explanations, and coherent
commits. These matter, but a passing repository check cannot establish
them. These remain expectations for contributors even when they need human
review. Do not label a guideline "enforced" because a test searches for an
approved phrase or class name.

Prefer preventing a bad operation in the code that performs it. Check
declarations mechanically when the declaration itself is the rule. Test
runtime behavior when the actual result is what matters. A test provides
evidence for the cases it exercises, not a guarantee about every case.

The source references identify inspected code, tests, and design notes.
We have not rerun those repositories' suites. A proposed extension is
identified as such; finding a useful donor does not make hello-world ready.


PART A. RULES TO BUILD INTO THE COMMON TOOLS
==========================================

A1. Commands, help, and choices
-------------------------------

Make is the usual entry point for setup, builds, tests, running the
project, and maintenance. CI calls the same commands.

Use names of the form <resource>[/<subject>]/<action>, for example:

    wheelhouse/acquire
    wheelhouse/check
    image/runtime/build
    test/unit/run
    deployment/status
    deployment/remove

Create only the targets the project needs. Instance names and other
choices are parameters. Use the same verbs for the same effects:

    acquire   Download selected external files or images.
    build     Produce something from inputs already available.
    check     Inspect without changing or repairing the inspected state.
    run       Execute work, including tests with temporary resources.
    create    Create something that remains after the command ends.
    apply     Update a selected deployment or configuration.
    status    Show existing state without changing it.
    remove    Delete the selected run's or deployment's resources.
    publish   Upload an artifact that has already been checked.

Derive help from the maintained command definitions. Bare make shows
tasks, prerequisites, effects, and examples. Keep prompts and side effects
out of Makefile evaluation: help, completion, discovery, and dry runs must
not prompt, contact Docker, download files, or change anything.

Offer a numbered menu when choices can be listed, such as saved contexts
or deployments. Resolve choices during execution. An explicit value stays
fixed; cancellation stops the command; unattended missing input fails
instead of waiting. Otherwise explain which input is needed.

Keep progress out of stdout when stdout contains a machine-readable value.

Checks: exercise help and dry runs without an engine or network; detect
unexpected writes and subprocess calls. Exercise explicit choices,
cancellation, and unattended use through the actual command entry point.
Help completeness and good names still need review.

Sources: [1], [2], [3].


A2. Settings and validation at input boundaries
-----------------------------------------------

Keep defaults and examples in Git, local preferences in an ignored file,
and secrets in separate private files. Load secrets only into the process
that needs them. Do not put their values in command lines, ordinary logs,
image layers, or recovery records.

Use one settings loader with a declared override order. Report effective
nonsecret settings and their sources when asked. Keep missing, empty,
and null values distinct where the contract distinguishes them. Read facts
from their maintained source instead of keeping a second handwritten copy.

Initialization creates missing files and preserves existing edits. Check
paths before writing and reject conflicts. A selected named deployment
keeps its identity, engine, and data location; a conflicting command-line
value cannot silently replace them.

Parse settings as data, never as shell or Make code. Construct argument
lists so user values stay literal and application arguments cannot add
Docker mounts, networks, or privileges.

Validate external inputs before acting: types, required fields, allowed
values, size limits, and relationships between fields. This includes
configuration, HTTP requests, files, and replies from other processes.
Type annotations alone do not validate those inputs. Use explicit
conversions and defaults; do not silently repair malformed values.
Accept or reject unknown fields according to the particular interface.

Checks: exercise invalid and boundary values through the owning validator,
literal shell-like arguments through launchers, override conflicts, and
repeated initialization with existing settings. Constructors or schemas
can prevent specific invalid states; they do not choose a sound contract.

Sources: [1], [3], [5], [6], [7].


A3. One selected Docker engine
------------------------------

Resolve an explicitly selected Docker context to an engine address once.
Pass that address through all work, nested commands, inspection, and
cleanup. A deliberately selected deployment configuration may supply it.
Do not silently substitute a different engine or ask again halfway through.

Construct the child environment explicitly. Clear inherited Docker,
Compose, builder, and proxy settings that could change the operation.
Give registry credentials only to acquisition or publication when needed.

Check rootless operation when it matters; a context name proves nothing.
Require an engine that can access the host paths used for bind mounts.
Recheck mutable facts before deleting or replacing resources.

Checks: run launcher tests with conflicting inherited settings and verify
the resolved endpoint reaches nested commands and cleanup. Separate live
engine checks establish capabilities needed by the chosen operation.

Source: [3].


A4. Acquisition, offline work, and the shared wheelhouse
------------------------------------------------------

Keep changing dependency choices separate from downloading the chosen
files. Builds and ordinary tests cannot access the internet, pull images,
update locks, or fetch missing tools. Installing verified local files is
allowed. Integration tests may use their declared private test services.

Prepare all external inputs: base images, Docker build frontends,
compilers, build backends, browser binaries, native libraries, and model
files. Account for downloads hidden in installation scripts. The fetching
tool itself needs a pinned, documented bootstrap path.

Give acquisition workers only their manifests, locks, necessary
credentials, and output locations. Do not mount application source,
runtime secrets, or a writable checkout. Apply dependencies to the project
in a separate offline step with only the required writable outputs.

Enforce offline access in the launcher and build configuration, including
image pulling and build initialization; setting a package manager's
offline flag alone is insufficient. Where acquisition has a required
route or destination limit, enforce it. A proxy environment variable
does not prevent a process from bypassing the proxy.

Reuse cached files first. Missing files produce the acquisition command
to run. Corruption, bad permissions, and engine failures remain errors;
they must not trigger an unexplained replacement download. Archive
extraction rejects escaping paths and bounds the extracted size.

Use one host-local wheelhouse across Python projects. Lockfiles select
versions and accepted hashes; the wheelhouse stores the bytes. Verify
platform compatibility and hashes before use. Give builds only their
selected files where practical.

Download to temporary files, verify completed bytes, and publish them
without exposing partial contents or overwriting another writer's result.
Concurrent writers must cooperate; preserve conflicts and report them.
Keep unrelated cache entries and retain the wheelhouse after each run.
Reuse the released wheelhouse tool. Other ecosystems keep their native
locks and caches while following the same rules.

Checks: build and test with internet access denied, including an empty
cache case that fails with acquisition instructions. Exercise corrupted
files, conflicting writers, and archive bounds in the responsible tool.
A failing download alone does not prove network isolation; see A6.

Sources: [4], [8], [9], [14].


A5. Build selected inputs and check the delivered artifact
---------------------------------------------------------

Construct a minimal build context. Exclude secrets, local settings,
unrelated caches, and temporary outputs. Reject unsafe paths or symlinks
and handle source changes where they could alter the selected inputs.
Local builds include intended worktree edits. Release and deployment
artifacts record the exact source and dependency inputs used.

Build once, check that artifact, and publish those same bytes. Run checked
images by digest or image ID; a tag can move. Determine rebuilds from
relevant inputs. Keep build and test dependencies out of the runtime
unless the product needs them.

Exercise what users receive: an installed Python wheel or sdist outside
the checkout; a JavaScript package's published files and public interface;
a frontend's built bundle and serving configuration; a backend image or
a native program's packaged executable.

Generated files have one generator and a no-write check for differences.
Lock updates remain an explicit command. Include newly added source
folders in builds and checks; do not rely on a stale handwritten inventory.

Checks: inspect the selected context and package contents, run installed
artifact tests, and verify publication uses the checked artifact identity.
Source-tree tests alone cannot establish that packaging works.

Sources: [4], [5], [6], [8], [9], [10], [11], [17].


A6. Container access and resource limits
----------------------------------------

Run project build tools, package managers, and tests in containers.
Keep host prerequisites small and explicit. A host helper needs a reason,
such as choosing Docker or inspecting Linux user IDs. State supported
operating systems and engine capabilities.

The launcher supplies these defaults:

- No network; read-only source and root filesystem where possible.
- Named writable outputs and bounded temporary storage.
- An explicit user with only the permissions the role needs, dropped
  capabilities, and no privilege escalation.
- CPU, memory, process, and log limits.
- No Docker socket, host namespaces, devices, or broad host mounts.

Declare exceptions by role. Only the worker needing a GPU, credential,
network, or writable directory receives it. Test services use private
networks; a local server binds only the selected interface.

Use measured UID/GID mappings for private host files. Do not assume
container UID 1000 is host UID 1000, make private files public, or change
ownership across a directory tree to make access work. Service user
selection and host-file ownership are separate concerns.

Checks: inspect actual launched containers when establishing or changing
the launcher. Exercise effective permissions and limits where necessary.
Reject unsupported required restrictions. A configuration-file check
does not prove that the engine applied the restriction.

A negative network test needs a reachable control destination from a
suitable control container. Without that control, report an inconclusive
test rather than claiming the network is blocked.

Sources: [2], [5], [6], [12].


A7. Ownership, deadlines, cleanup, and recovery
----------------------------------------------

Record which resources a run or selected deployment owns and which it
borrows. Use ownership identifiers that survive interrupted creation.
Names or timestamps alone do not authorize deletion. Isolate concurrent
runs and prevent conflicting operations on the same retained resource.

For temporary resources, stop their consumers, remove owned containers,
networks, and volumes, confirm removal, then delete temporary inputs.
Do this on success, failure, and cancellation. Keep the original failure.
If work succeeds but required cleanup fails, return failure. Optional
cache maintenance has a separate result and may be deferred.

Keep shared caches, persistent data, settings, secrets, and requested
outputs. Provide explicit removal commands where needed. Routine cleanup
must not use global Docker prune. A borrowed database or sibling fixture
is removed only by its owner, after consumers stop; use the same test
executor for borrowed and newly created fixtures.

Finite jobs have an overall time budget with time reserved for bounded
cleanup. Nested work receives the remaining work time. Expiry of the work
budget must not consume or skip the cleanup allowance. Retries have limits.
Services have bounded startup, requests or jobs, and shutdown; their
intended running lifetime is a separate matter.

Killing a Docker client does not prove the daemon stopped its work.
Failed inspection does not prove absence. Retain files a surviving process
may need and report identifiers and recovery commands when stopping or
removal is unconfirmed. SIGKILL and host crashes cannot be handled by exit
traps. Use labels or a small saved record when work can outlive its caller.

Checks: exercise success, failure, cancellation, selected deadline and
interruption cases, and concurrent ownership. Assert cleanup order and
primary-error preservation. The promise is safe cleanup or retained
ownership and recovery information, not that every crash leaves nothing.

Sources: [1], [2], [3], [4], [9], [10], [13].


A8. Carry useful errors to the caller
-------------------------------------

Implement error propagation through startup, configuration, builds,
tests, workers, services, APIs, clients, and background work. Preserve
the original cause when adding context. Catch only errors the code can
classify or handle. An unexpected defect, storage failure, or transport
failure must not become "invalid input", an empty result, or success.
ValueError or TypeError alone does not establish bad caller input.

Use stable codes for machine decisions alongside useful explanations.
Clients must not have to parse prose or infer the cause from an HTTP status.
Carry operation, phase, and request or job identifiers across process
boundaries. Retain messages, causes, and useful stack locations for the
appropriate recipient.
An unfamiliar error code must not erase its explanation. Keeping a Python
cause is insufficient if the final CLI or GUI shows only "failed".

Shell, Make, pipeline, and subprocess wrappers preserve failure status
and useful stderr. Retain original exit codes or signals where useful.
A continuing service can remain healthy after a failed job, but must
report that job's failure to its caller.

Keep caller cancellation, dependency timeout, and the caller's deadline
distinct. Cancellation remains cancellation after bounded cleanup.
Retain independent failures and identify work whose stopping is unconfirmed.

Track effects accurately: rejected, not started, completed, still running,
or unknown. A lost reply or timeout does not prove a mutation failed,
a worker stopped, or a result was not accepted. Do not retry unless both
the failure and the operation's repeat behavior allow it; see B3.

Keep primary failures separate from cleanup, logging, diagnostic-storage,
and error-delivery failures. Continue independent required cleanup. An
error while printing a report must not erase the original cause or release
ownership of work still running.

Once a response has started or may have started, do not send a replacement
unless the protocol supports it. Better diagnostics must not rewrite an
accepted result or a saved command awaiting exact replay.

Redaction and retained diagnostics
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

At a boundary that knows configured secrets, redact those values and their
relevant encoded forms before truncation. Remove credentials, private keys,
passwords, tokens, cookies, signed access URLs, and other material identified
as confidential for that context. Pattern matching cannot find every secret.

Render the result as literal text, handle terminal controls or markup,
bound its size, and mark omissions. Escaping and truncation are not
redaction. Avoid wholesale dumps of jobs, results, environments, headers,
conversations, or traceback locals.

Some information has a narrower audience. For example, a public
authorization error may conceal whether a private resource exists while
authorized operators receive the protected reason linked to that error.
Implement these specific restrictions instead of suppressing every
unfamiliar exception. Scientific input, a useful path, an offending scalar,
or a remote component's message is not automatically secret.

Retain diagnostics that must survive cleanup or restart in a bounded,
protected location with an inspection command and removal policy. Only
point to evidence actually retained. Its lifetime is separate from the
temporary work that failed.

Checks: carry a distinctive cause through each changed reporting path
to its actual CLI output, API response, UI, or saved report. Assert status,
cause, context, known effects, and appropriate diagnostic access. Include
unexpected defects and secondary failures where those paths exist.
Put synthetic secrets inside useful messages, including near size limits;
the secret must disappear while the explanation survives. These checks
exercise known cases; they do not certify that all secrets are detectable
or that every explanation is helpful. Those judgments belong in Part C.

Some donor renderers still hide unfamiliar exception messages. That is
a gap to fix, not a convention to copy. Reuse their useful propagation
and redaction mechanisms without inheriting blanket suppression.

Sources: [5], [6], [7], [10], [14], [15], [16], [18].


A9. Repository checks and CI permissions
----------------------------------------

Provide fast repository checks in an offline, confined container with a
read-only checkout. They need no product services, production secrets,
model weights, or GPU. Live engine and service tests have separate commands.
Fast tests can exercise launcher logic without controlling the engine.

Cover the concrete rules above: command side effects, literal inputs,
engine selection, offline access, build inputs, generated-file drift,
permissions, cleanup, and absence of checkout debris. Where the project
has chosen important module boundaries, check forbidden import directions.
Do not impose one architecture on every project.

A test command or requested selection that finds no tests fails clearly.
Offer focused selection through the existing suite; whole-suite commands
remain whole. Report which tests ran and put actionable failures after
routine output and cleanup.

CI uses the same Make commands. Check jobs have read-only repository
permissions and no publication or production credentials. Pin external
actions to full commits; disable persisted checkout credentials. Limit
publication permissions and release triggers to explicit publication jobs.

Checks: inspect workflow permissions, action pins, checkout behavior,
and allowed publication events. Check important import boundaries where
declared. Repository files cannot prove that external branch, tag, or
environment protections have been configured; verify those separately
before relying on them.

Sources: [3], [4], [6], [10], [11].


PART B. EXTRA MECHANISMS WHEN A PROJECT NEEDS THEM
================================================

B1. Optional dependencies and supported interfaces
--------------------------------------------------

Keep optional HTTP, database, browser, and model dependencies with the
features that use them. Install the basic package without extras and test
its supported imports and functions. Loading the core must not eagerly
load an optional adapter. This does not require every core to have zero
dependencies. Report a missing requested capability clearly; do not catch
every ImportError and mislabel a broken installed component as absent.

For public packages, CLI commands, APIs, configuration, and saved formats,
declare the interfaces and versions supported. Test those actual promises
with compatible clients, artifact tests, and contract comparisons as
appropriate. A schema diff alone does not establish behavior compatibility.
Update generated clients deliberately; deployment must not silently
regenerate them against a different sibling checkout.

An archived snapshot is not automatically a supported release. In the
inspected NMR provider API, prerelease archives explicitly have no supported
compatibility baseline. A template must let a project make that choice
honestly while still protecting data it promises to retain.

Mechanisms and checks: dependency groups and lazy adapter imports; a minimal
installation test; a declared support policy and tests against the selected
versions. Choosing the promise and retiring it require review.

Sources: [6], [10], [18].


B2. Retained state, upgrades, and recovery
-----------------------------------------

Write retained files or records through an owner that provides complete
old or complete new state. Use atomic replacement or a transaction, and
locks or expected-version checks for competing writers. Preserve corrupt
or unsupported state and report it; do not silently reset it to empty.
Atomic visibility alone does not promise survival after a power loss.
If an acknowledgement promises durable storage, implement that stronger
guarantee explicitly.

Database runtime credentials have only the access the application needs;
schema administration is separate. Test upgrades from supported predecessors
with representative populated data, not just an empty database. Check
preserved relationships, interrupted migration and retry, and compatibility
with old writers where coexistence is promised. State when old writers must
stop. Keep historical conversion rules stable. Refuse a downgrade that
would discard required data; reverting application code does not by itself
reverse a data migration.

Use separate retention rules for inputs, results, pending work, audit
history, and diagnostics. Remove only eligible records whose live references
allow it. Make large cleanup jobs bounded and resumable, without letting
one busy record prevent progress forever.

For irreplaceable data, state what must be backed up together, document
restoration into a compatible version, and test the restored data for
actual usability. This is a proposed requirement: the review did not
establish a reusable, complete backup and restore implementation among
the donors inspected.

Mechanisms and checks: atomic write helpers or database transactions,
conflict detection, populated migration tests, and focused corruption,
interruption, and retention tests. The process-status file and delivery
store in [18] provide concrete but different examples; neither makes every
kind of state equally durable.

Sources: [6], [18]. Backup and restore: proposed extension.


B3. Services, background work, and safe repetition
------------------------------------------------

Distinguish a running process from initialized, ready, available for more
work, and draining. Publish readiness from the actual owned runtime;
expired status or a reused process ID must not imply readiness.

Bound accepted work by count and, where payloads vary materially, by size.
Refuse or defer work before accepting more than can be retained safely.
On shutdown, stop admission, finish or account for accepted work within
the deadline, and close storage and other dependencies last.

For operations that may be repeated after a lost reply or restart, define
an operation identity and duplicate/conflict behavior. Persist the original
intent when recovery depends on it. Acknowledge durable acceptance only
after the relevant commit. "Queued here" and "accepted by the remote
service" are different states. Reconcile unfinished operations after restart;
do not rerun a scientific computation merely to resend its result.

Mechanisms and checks: admission limits, readiness state, bounded shutdown,
and the transaction, idempotency key, or retained delivery queue the workload
actually needs. Test rejection before side effects, drain ordering, and
selected duplicate, lost-reply, and restart cases. A retry loop alone does
not provide safe repetition or exactly-once effects. Simple services need
not acquire a universal queue framework.

Sources: [6], [18].


B4. Credentials and trusted HTTP ingress
----------------------------------------

Where a service issues or manages credentials, define creation, activation,
expiry, replacement, revocation, and recovery after compromise. Setup
preserves identity or reports a conflict. The verifier enforces the states
and validity periods the credential scheme supports. Removing a private
copy is not the same as revoking its public authority; state how already
issued capabilities are affected.

For proxy deployments, configure trusted peers, the forwarding convention,
and the public origin and scheme. Normalize only trusted metadata and
reject contradictions before authentication or application effects.
Do not trust a forwarding header because it is well formed.

Mechanisms and checks: explicit management operations and verifier tests;
real server-stack tests for the intended proxy path and spoofed alternatives.
The donors provide credential-state and ingress checks, not a universal
rotation system. Trust choices and recovery procedures require review.

Source: [6].


B5. Frontend state and usable interfaces
----------------------------------------

Tie asynchronous results to the request and view that own them. An older
response must not overwrite a newer selection or cancel unrelated work.
Represent pending, confirmed, rejected, and unknown outcomes accurately.
Preserve unsaved work across the navigation and recovery cases the product
promises, and make an intentional discard explicit.

Use a locked toolchain, typechecking, built-bundle checks, and focused DOM
and browser tests. Use semantic controls and explicit loading, empty,
success, and failure states. Test request races and actual navigation behavior.
Exercise essential controls with a keyboard, touch, narrow screens, and
zoom; long identifiers must remain accessible in full.

Mechanisms and checks: request ownership, explicit state transitions,
draft retention where promised, and tests through the actual UI. Automated
accessibility checks cover only part of usability. The NMR GUI has useful
request-lifetime tests; its unsaved-work note also records remaining gaps.
Treat those gaps as requirements to address, not implemented guarantees.

Source: [10].


B6. Large assets and integration across repositories
---------------------------------------------------

ML projects acquire and verify model code, configuration, tokenizers,
preprocessing files, and weights explicitly. Grant GPU access only to
the workers that need it. Keep ordinary software tests independent of
large assets where possible.

Shared integration tests use each repository's supported commands and
exchange endpoints, identifiers, and ownership explicitly. The creator
cleans up a fixture after all consumers stop; borrowers do not destroy it.

Mechanisms and checks: pinned asset manifests and verification, separate
heavy-test commands, and fixture setup and teardown with ownership checks.

Sources: [4], [7], [13], [14], [15], [16].


PART C. GUIDELINES FOR PEOPLE AND CODE REVIEW
============================================

C1. Architecture and understandable tools
-----------------------------------------

Give important rules and state changes a clear owner. Keep application
logic independent of HTTP, deployment, and optional adapters where those
boundaries help the project. Decide the important dependency directions
before adding import checks. A clean import graph does not prove a good
design.

Abstract repeated mechanics when real callers benefit; do not force
different domain facts through one generic abstraction. Group tools by
their job. Add files, flags, wrappers, and directories for a clear purpose.
Keep the normal path readable and complicated error handling in small,
named helpers. Do not turn the template into a universal workflow engine.

Use pinned shared tools rather than copying another context selector,
downloader, or cleanup engine into every project. When copying is justified,
record the source and adaptations and provide an update procedure that
preserves local edits. Keep one useful operator guide and short agent
instructions, with current behavior separate from plans.
After a command, explain the result and show the next useful command
when there is one.

Sources: [1], [2], [3], [4], [6], [8].


C2. Contracts, permissions, and honest explanations
--------------------------------------------------

Decide what external inputs mean, what defaults are safe, which interfaces
are public, and what compatibility users can rely on. Remove obsolete
internal aliases and shims when they serve no real caller. Do not break
a public promise or discard existing data just because the code is young.

Choose permissions, network exceptions, retention periods, trusted proxies,
and confidential fields from the actual workload. Record those choices
where the enforcing code reads them. Review whether the choices remain
appropriate; tests cannot make that decision.

Show the most useful explanation available, with sensitive material
removed. Explain the operation, component, actual cause, useful field or
location, expected and observed values where relevant, completed and
uncertain effects, and the next reasonable action. A request ID helps find
evidence; it does not replace an explanation already available.

Attribute a model's or remote endpoint's explanation to its producer and
say when it is unverified. Do not substitute an older, familiar cause for
the current failure. Preserve useful excerpts for authorized recipients
instead of treating all scientific values, paths, or unfamiliar messages
as confidential. Review the final report for clarity and context as well
as testing the propagation and redaction machinery.

Sources: [5], [6], [7], [10], [14], [15], [16], [18].


C3. Commit discipline
---------------------

Before editing, check the requested branch, current revision, and working
tree. Preserve other people's edits, including staged changes, and keep
them out of your commit. Keep each commit small enough to review and
complete enough to understand: related code, focused tests, documentation,
and necessary migration instructions.
Separate unrelated formatting, refactoring, and dependency changes.

For a behavior bug, demonstrate a focused regression test failing for the
intended reason and passing after the fix. Record the results. Preserve a
separate test/fix commit sequence when the task requests it.

Read the final diff and run the narrowest meaningful checks on those final
files. Later edits require the affected checks again. Report failures and
checks that could not run; a focused pass is not a full-suite pass.

Stage explicit paths and inspect the exact staged diff and file list.
Respect named-file scope; explain a conflict before widening it. Do not
sweep unrelated work into a commit with blanket staging or commit-all.

Use a concise imperative subject and a short body explaining what changed,
why, what was checked, and what remains unverified. Fold corrections into
your own unpushed commits when that improves the history, while preserving
requested test/fix history. Do not rewrite shared history or discard other
people's work without explicit instruction.

Follow the task's commit and push instructions. Check the latest remote
state and preserve concurrent changes. Respect merge and release
conventions so ordinary work does not trigger publication. Report what
was committed, pushed, and left unfinished.

Git can show branch, revision, staged paths, and exact content; hooks can
check message structure. Those are mechanical aids, not proof of coherent
scope, truthful explanations, or sufficient testing. Do not use a blanket
every-commit-must-pass gate to block a requested regression-test/fix history.

Sources: [1], [3], [6], [8], [9].


C4. Test the important behavior without building a testing bureaucracy
---------------------------------------------------------------------

The first useful version already includes safe inputs, suitable container
permissions, and cleanup, with focused tests introduced alongside them.
Add database, browser, restart, upgrade, and live-service tests when those
features exist. Test a fix where its defect can be reproduced. Broaden
testing when the change creates a concrete reason.

Test accepted inputs, refusals, effects, and diagnostic meaning. Avoid
exact private wording or source-spelling checks unless that structure is
itself the rule. Do not mistake test count or coverage percentage for
proof of good behavior. Do not require exhaustive failure campaigns,
repeated full-suite runs, or a reporting framework before useful work can
ship. Style checks enforce the project's chosen rules, not every donor's
preferences.

Sources: [3], [4], [6], [10].


First implementation and decisions still to make
------------------------------------------------

Start with one complete example: choose a project identity and type,
explain the supported host setup, show the commands, create local settings,
acquire dependencies, build and test offline, run, and clean up. Verify
that two fresh projects can share one engine and wheelhouse without names,
ports, or cleanup interfering. Include a failure that leaves a useful
report and either cleaned resources or explicit recovery information.

Decide how a new repository selects its project type and replaces template
names. Decide which tools are pinned shared dependencies and which small
files belong to each generated project. Record an intentional update path
that preserves project edits. A generator, a collection of starter folders,
and the exact shared-tool boundary have not been selected by this note.

Then add another project type using the same working tools. Mark each
implemented rule with its actual entry point and check command, and leave
unimplemented rules visibly planned. Do not describe the template as
enforcing this note merely because the note has been committed.
