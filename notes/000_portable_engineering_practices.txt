Hello World: how new projects should work
========================================

9 November 2026
Repository: numpde/hello-world
Plan for the template; written before implementation.

The aim
-------

A new project should be useful from the first checkout. Running make
should explain the available commands. After explicitly downloading its
dependencies, a developer should be able to build, test, and run the
project without surprise downloads or unwanted temporary files left behind.

The template should work for packages, command-line tools, backends,
frontends, and mixed projects. Keep the common tools small. Add database,
browser, GPU, and release tools when the project needs them.

Document the supported operating systems and Docker setup. A command
that depends on Linux must say so. Keep those dependencies in the
development tools, out of application code.

These rules come from inspecting the repositories listed at the end.
They describe what hello-world should provide. We have not rerun the
source repositories' test suites for this review.


1. Make should tell people what to do
------------------------------------

Make is the usual entry point for setup, builds, tests, running the
project, and maintenance. CI calls the same commands.

Use names of the form:

    <resource>[/<subject>]/<action>

For example:

    wheelhouse/acquire
    wheelhouse/check
    image/runtime/build
    test/unit/run
    deployment/status
    deployment/remove

Create only the targets the project needs. Put instance names and other
choices in parameters. Name the thing being operated on: test-runner
image, runtime image, database, or deployment.

Use verbs consistently:

    acquire   Download selected external files or images.
    build     Produce something from files already available.
    check     Inspect existing inputs without changing or repairing them.
    run       Execute work, including tests with temporary resources.
    create    Create something that will remain after the command ends.
    apply     Update a selected deployment or configuration.
    status    Show existing state without changing it.
    remove    Delete the selected run's or deployment's resources.
    publish   Upload a package or image that has already been checked.

Add another verb only when it names a distinct useful action.

Bare make should show the main tasks, prerequisites, effects, and useful
examples. Keep help and targets in sync. Avoid several independent lists
of supported commands.

When choices can be listed, such as Docker contexts or saved deployments,
offer a numbered menu. Otherwise explain the missing input. A supplied
value stays fixed. Unattended commands fail clearly instead of waiting
for input. Users must be able to cancel.

Help, completion, discovery, and dry runs must not prompt, contact Docker,
download files, or change anything. Do this work only when a command runs.

Print the result and the next useful command. Keep progress messages out
of stdout when stdout is meant to contain a value for another program.

Sources: [1], [2], [3].


2. Keep settings in one place and secrets separate
-------------------------------------------------

Keep project defaults and examples in Git. Keep local preferences in an
ignored settings file. Keep secrets in separate private files.

Give secrets only to the process that needs them. Keep their values out
of command lines, ordinary logs, image layers, and recovery records.

State which command-line values can override local settings. Show the
effective nonsecret settings and where they came from when asked.
Distinguish a missing value from an explicitly empty one.

Remembering a wheelhouse path is useful. Silently choosing a different
Docker engine or deployment is dangerous. Those choices must be explicit,
either in the command or in a configuration the user deliberately selects.

When deployments are added, each named deployment keeps its own settings.
A conflicting command-line value must not quietly change its identity,
data location, or engine.

Initialization creates missing settings and preserves existing edits.
Check existing paths before writing. Report conflicts instead of
overwriting configuration or secrets.

Parse settings as data; do not execute them as shell or Make code.
Pass user values as literal arguments. Application arguments must not be
able to add Docker mounts, networks, or privileges.

If information already exists in a maintained file, read or calculate it
from that file. Avoid another manually edited copy. For example, do not
maintain two dependency-version lists and add tests to keep them equal.

Sources: [1], [3], [5], [6], [7].


3. Choose Docker once for the whole command
------------------------------------------

Choose a Docker context explicitly. Resolve it to an engine address and
use that same address for all work, nested commands, inspection, and
cleanup. A deliberately selected deployment configuration may supply
the choice.

Clear inherited Docker, Compose, builder, and proxy settings that could
change the command. Pass the settings it needs explicitly. Give registry
credentials only to the download or publication step that needs them.

Do not infer rootless operation from a context's name. Check the engine
when that property matters. Commands using local bind mounts must use an
engine with access to those host paths.

Once a choice is made, carry it through the operation without asking
again. Recheck facts that may have changed before deleting or replacing
resources.

Source: [3].


4. Download first; build and test offline
---------------------------------------

Use separate commands for updating dependency choices and downloading
the chosen files.

Builds and ordinary tests must not access the internet, pull images,
update locks, or fetch missing tools. Installing from verified local
dependencies is allowed. Integration tests may talk to their declared
test services on private networks.

Prepare everything needed for offline work, including base images,
Docker build frontends, compilers, build backends, browser binaries,
native libraries, and model files. Account for downloads hidden inside
package installation scripts.

When unpacking downloads, reject paths outside the destination and limit
the total extracted size.

A download job gets only the manifests, locks, credentials, and output
locations it needs. It must not receive application source, runtime
secrets, or writable access to the checkout. If installing dependencies
must write to the project, do that in a separate offline step with access
only to the intended outputs.

Reuse cached files before requesting network access. If a dependency is
missing, explain which command obtains it. Corruption, bad permissions,
or an unavailable engine must not silently trigger a replacement download.

Where downloads must follow a chosen route or contact only certain
servers, enforce that restriction. Merely setting a proxy variable does
not prove that a process cannot bypass it.

Shared wheelhouse
~~~~~~~~~~~~~~~~

Use one host-local wheelhouse across Python projects. Lockfiles choose
the versions and accepted hashes; the wheelhouse stores the files.

Select files compatible with the project's Python version and platform.
Verify their hashes before use. Give each build only its selected files
where practical.

Add missing files without disturbing unrelated contents. Download to
temporary files and check the completed bytes. Never expose partial
downloads to readers or overwrite another writer's result. Concurrent
downloads must cooperate. Preserve conflicting files and report them.

Keep the wheelhouse after builds and tests. Cleanup of a temporary run
must not remove dependencies shared with other projects.

Reuse the released wheelhouse tool instead of writing another downloader
in each project. Other languages keep their normal lockfiles and caches
while following the same rules.

The tool used to fetch dependencies also needs a pinned, documented
installation path. A fresh checkout must not depend on an unexplained
tool already installed on the developer's machine.

Sources: [4], [8], [9], [14].


5. Build the selected code and test the result
--------------------------------------------

Send only the files a build needs to Docker. Exclude secrets, local
settings, unrelated caches, and temporary outputs. Check unsafe paths,
symlinks, or file changes where they could alter what enters the build.

Local development builds must include the intended worktree edits.
For releases and deployments, record the exact source and dependencies
used. Do not rebuild an artifact after checking it and then publish the
replacement as though it were the checked artifact.

Use an image digest or image ID when running a checked image. Tags can
change. Rebuild a component when its relevant inputs change, without
invalidating every other component unnecessarily.

Keep build tools and test dependencies out of the runtime unless the
product actually needs them.

Test what users will receive:

- Install a Python wheel or sdist and test it outside the source checkout.
- Check a JavaScript package's published files and public interface.
- Exercise a frontend's built bundle and serving configuration.
- Run a backend's built image or a native program's packaged executable.

These tests catch missing packaged files and runtime dependencies that
source-tree tests can miss.

Generated files have one generator and a check that reports differences
without rewriting them. Updating a lockfile is a separate deliberate
operation because package indexes change over time.

Sources: [4], [5], [6], [8], [9], [10], [11], [17].


6. Give containers only what they need
-------------------------------------

Run project build tools, package managers, and tests in containers.
Keep host prerequisites small and documented. A host helper needs a
specific reason, such as selecting Docker or inspecting Linux user IDs.

Start with:

- No network.
- Read-only source and root filesystem where possible.
- Explicit writable outputs and limited temporary storage.
- A user with the minimum required permissions.
- Dropped Linux capabilities and no privilege escalation.
- CPU, memory, process, and log limits.
- No Docker socket, host namespaces, devices, or broad host mounts.

Give network access, a GPU, credentials, or a writable directory only
to the container that needs it. Tests with a database can use a private
test network. A local web server should bind only the intended interface.

Do not assume that UID 1000 inside a container is UID 1000 on the host.
Use the shared identity-mapping helper when private host files require
it. Keep those files private; do not fix access by making them public
or changing ownership across an entire directory tree. Service users
inside containers are a separate choice from host-file ownership.

Check the actual container settings when establishing or changing the
launcher. Where necessary, check the effective permissions and limits
inside the container too.

If a platform cannot enforce a required restriction, report that and stop.

To test blocked network access, first establish that the destination
can be reached from a suitable control container. Otherwise a failed
connection proves little; report the test as inconclusive.

Sources: [2], [5], [6], [12].


7. Finish or stop cleanly
------------------------

Every command must distinguish resources belonging to its run or selected
deployment from resources it borrows. Record enough information to find
what it created, including after an interrupted Docker call.

Delete only resources known to belong to that run or deployment. Never
infer ownership from a familiar name or an old timestamp. Concurrent
runs must not collide or delete each other's work.

For temporary resources, cleanup happens in this order:

1. Stop the processes and containers using temporary inputs.
2. Remove the run's temporary containers, networks, and volumes.
3. Confirm that removal finished.
4. Delete the temporary inputs.

Do this on success, failure, and cancellation. Keep the original error
visible. If the work succeeded but required cleanup failed, report
failure. Optional maintenance of old caches or images reports its own
result and may be deferred without failing a successful build.

Keep shared caches, persistent data, configuration, secrets, and requested
outputs. Give each an explicit removal command when one is needed.
Routine cleanup must not use global Docker prune.

If a test borrows a database or another repository's fixture, it must not
destroy it. A command that creates the fixture may remove it after all
consumers have stopped. Use the same test code in both cases.

Deadlines and uncertain outcomes
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Builds, tests, and maintenance jobs need an overall deadline and time
to clean up. Nested commands share the remaining time. Retries have a
limit and apply only to failures that might succeed on another attempt.

Services need bounded startup, individual requests or jobs, and shutdown.
Their intended running lifetime is separate from those limits.

Killing the Docker client does not prove that a build or container stopped.
If inspection fails, do not assume the resource has gone. Keep files that
a surviving process may still need, report what may remain, and provide
the command or identifiers needed to inspect and recover it.

Exit traps cannot handle SIGKILL or a host crash. If work can outlive the
command, keep enough ownership information to find and clean it up later.
Container labels or a small saved record may be enough; a separate record
is not required for every helper.

Sources: [1], [2], [3], [4], [9], [10], [13].


8. Keep checks useful and failures readable
------------------------------------------

Provide a fast repository-check command. It runs offline in a confined
container, reads the checkout without changing it, and needs no product
services, production secrets, model weights, or GPU.

Tests that start services or manage live Docker resources have separate
commands. The fast checks can test launcher logic without controlling
the engine.

Check mistakes that matter:

- Make help and dry runs cause no side effects.
- User values cannot execute code or change Docker options.
- Commands use the selected engine.
- Offline commands cannot start downloading.
- Build inputs exclude private and unrelated files.
- Dependency files and generated files are consistent.
- Containers have the intended permissions and writable paths.
- Temporary resources are cleaned up correctly.
- Tests do not leave bytecode, caches, or build output in the checkout.

When source folders are added, include them in the appropriate builds
and checks. Do not let an old file list silently omit new code.

Prefer tests of behavior: accepted input, rejected input, resulting
effects, and useful error information. Avoid pinning exact private
wording or checking source spelling when behavior is what matters.
Use source-layout checks only where the layout itself protects a rule.

A test command or requested selection that finds no tests must fail
clearly. Offer focused selection through the existing suite, and keep
whole-suite commands whole.

Show actionable failures at the end, after routine output and cleanup.
Keep full diagnostics available. Preserve the original failure and
report cleanup problems separately. Say which tests actually ran.

Testing priorities
~~~~~~~~~~~~~~~~~~

The first working version includes safe input handling, appropriate
container permissions, and cleanup. Add focused tests for those rules
as the relevant code is introduced.

Add database, browser, restart, upgrade, or live-service tests when the
project needs those features. Test a fix at the level where the defect
can be reproduced. Run broader tests when the change creates a reason
to do so.

Do not require exhaustive failure testing, repeated full-suite runs, or
a new reporting framework before delivering a useful working project.
Style checks should enforce chosen project rules, not every preference
found in the source repositories.

Sources: [3], [4], [6], [10].


9. Add the tools each project needs
----------------------------------

A Python package needs packaging and installed-package tests. A frontend
needs a locked JavaScript toolchain, typechecking, bundle checks, and
appropriate browser tests. A native program needs a prepared compiler
and runtime packaging.

A backend adds service configuration, health checks, and shutdown.
A database adds restricted runtime credentials, separate schema
administration, migrations, and disposable database tests.

An ML project adds explicit model downloads, file verification, and
optional GPU access. Pin model code, configuration, tokenizers, and
preprocessing files as well as weights. Keep ordinary software tests
independent of large assets where possible.

When repositories run a shared integration test, use each repository's
supported commands. Exchange the necessary endpoints and identifiers
explicitly, and agree which process creates and removes each service.

A release workflow checks a concrete package or image, then publishes
those same bytes with credentials limited to publication.

These additions must follow the same commands, configuration, and cleanup
rules. Their existence does not require a universal workflow engine or
a plugin system inside the template.

Sources: [4], [7], [8], [9], [10], [11], [13], [14], [15], [16], [17].


10. Keep the tools understandable and maintainable
-------------------------------------------------

Use pinned releases of suitable shared tools. For copied code, record
where it came from and how it was changed. Provide a deliberate update
procedure that preserves the project's own edits.

Group tools by what they do. Add files, directories, flags, and helpers
when they have a clear purpose. Keep the normal workflow easy to follow;
put complicated error handling behind small, named functions.

Keep one useful operator guide and short instructions for coding agents.
Separate current behavior from future plans. CI uses the same Make targets
and gives publication permissions only to publication jobs.

First build one complete example: explain its commands, choose settings,
download dependencies, build and test offline, run, and clean up. Then
add other project types using those same working tools.

Sources: [2], [3], [4], [8].
